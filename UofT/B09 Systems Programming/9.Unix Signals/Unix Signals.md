# Unix Signals
[[Unix Signals|Signals]] are how the [[Kernel|kernel]] notifies [[Unix Process Creation|processes]] of certain events and severe errors.

![|350](https://miro.medium.com/v2/resize:fit:1200/1*2G4M3aX6-gyqjALmXyE6Jw.png)

A [[Unix Signals|signal]] is just a constant representing a type or a case. It carries no data with it.

---
## Examples

![Signal Examples|350](https://miro.medium.com/v2/resize:fit:1068/1*d3oj7WxSDUZDz_GmrltOrw.png)

- `SIGINT`: Interrupt. 
  Typically generated by `Ctrl + C` in the terminal.
- `SIGPIPE`: Broken pipe.
  Wrote to a pipe/socket with no reader left.
- `SIGSTOP`/`SIGCONT`: Suspend/resume a process.
- `SIGCHILD`: A child died, was suspended, or was resumed.
- `SIGTERM`: Request for graceful termination. 
  The shell `kill` command's default signal.
- `SIGKILL`: Hard request for termination.
  Cannot be caught, blocked or ignored.
- `SIGBUS`/`SIGSEGV`: Illegal memory access.
- `SIGUSR1`/`SIGUSR2`: Application specific as we define.

## Signal Lifecycle

![image|400](https://notes-media.kthiha.com/Unix-Signals/bac86b4bb118676cf874ed1e055263a2.png)

1. Some event **generates** a [[Unix Signals|signal]].
   Eg:
	- a hardware error.
	- another [[Unix Process Creation|process]] calling `kill()`
	- the [[Kernel|kernel]] detecting a broken [[File Redirection & Pipes|pipe]]
2. The [[Kernel|kernel]] tries to **deliver** the [[Unix Signals|signal]] to the target [[Unix Process Creation|process]].
3. **Until delivered**, the [[Unix Signals|signal]] is `pending`.
   Common cause of prolonged pending is:
	- A process can `mask`($\text{a.k.a block}$) a signal
	- While masked, the signal remains undelivered till the process unmask it.
4. **Upon delivery**, one of several default actions happen:
	- ignore
	- suspend the process
	- resume the process
	- kill the process
	- kill the process with memory dump.
	
	Note that 
	- Most of these default actions are **overridable**.
	  You can install your own signal handler function instead.
	- **Exception**: `SIGKILL` and `SIGSTOP` cannot have their action changed.
5. **After delivery**, 
	- If the signal was **ignored**
	- or if the handler ran and **returned normally**,
	- the process's normal execution simply **resumes**.
	- But if a handler interrupted a **blocked system call**,
	- that system **fails** with `EINTR` by default.

**No multiplicity or queuing**
- The kernal only tracks which types of signal are currently pending, not how many times each have occurred.
- If the same signal type generated twice while its blocked, the process only sees one pending instance once it unblocks.
- Hence, the handler should account for the possibility that multiple events occurred even though one signal delivery happened.

## Programmatically Generating a Signal 
From the shell, we can use
```bash
kill -SIGKILL 31337
kill -KILL 31337
kill -9 31337
```

For C via system calls, we can use
```c
int kill(pid_t pid, int sig);    // send `sig` to process `pid`
int raise(int sig);              // send `sig` to yourself (the calling process)
```

## Code Snippets
### Basic Handler
```c
void handler(int sig) {
    write(STDOUT_FILENO, "caught!\n", 8);
}

struct sigaction sa = { .sa_handler = handler, .sa_flags = 0 };
sigemptyset(&sa.sa_mask);
sigaction(SIGINT, &sa, NULL);
```

### Ignoring SIGPIPE
```c
struct sigaction sa = { .sa_handler = SIG_IGN, .sa_flags = 0 };
sigemptyset(&sa.sa_mask);
sigaction(SIGPIPE, &sa, NULL);

ssize_t n = write(fd, "hello", 5);
if (n == -1 && errno == EPIPE)
    printf("nobody's reading\n");
```
